## Scope and baseline

This was a read-only implementation audit followed by this report. No compiler,
frontend, driver, codegen, runtime, public header, package, or test behavior was
changed.

A fresh Release baseline at
`/tmp/matcore-ir-v1-cpu-planner-baseline.bCPEvg` built 19/19 steps and passed
8/8 CTest tests in 62.43 seconds. The baseline includes the native frontend,
driver/adversarial pipeline, integration matrix, relocated installed consumer,
and CPU GEMM runtime.

The milestone must preserve:

- native Clang authentication and exact SourceManager ranges;
- deterministic JSON IR v0 and bootstrap/native differential coverage;
- source rewrite and generated sites/stubs/backend behavior;
- the stable C ABI v0 and synchronous reference GEMM;
- ordinary relocatable objects and external Clang linking;
- dependency-race defenses, install relocation, and consumer regeneration;
- explicit errors, no hidden copy/allocation, and no silent fallback.

CUDA, HIP, Metal, NPU, MLIR lowering, heterogeneous placement, fusion,
autotuning, GEMV, GEVM, and ReLU-GEMM remain outside this milestone.

## Current-state findings

### JSON v0 and its in-memory capture DTO are not equivalent

`compiler/lib/ir/matcore_ir.h` stores matrix role, source expression, and
mutability, but the deterministic serializer currently synthesizes these
semantic fields:

- f32 element type;
- rank 2;
- dynamic shapes and contiguous strides;
- row-major layout and host residency;
- output/input no-alias requirements;
- read/write effects and synchronous execution.

The parser validates those fields and then discards most of them. Consequently,
extending the current DTO in place would allow typed v1 semantics to be silently
lost through the existing v0 code generator.

### The safe insertion seam is downstream of capture

The native and compatibility frontends should initially remain unchanged. The
safe boundary is after frontend extraction and existing v0 verification, but
before serialization/codegen:

```text
native/bootstrap capture DTO
  -> existing v0 verifier
  -> explicit v0-to-v1 conversion
  -> typed v1 verifier
  -> capability-aware planner
  -> loss-checked v1-to-v0 CPU ABI projection
  -> unchanged rewrite/codegen/runtime path
```

This preserves source snapshots, site IDs, source ranges, diagnostic identity,
and generated bytes while v1 becomes trustworthy.

### Runtime is the lowest-risk planning integration point

Generated backend code currently forwards directly to
`matcore_runtime_gemm_f32_v0`. The runtime already performs the complete
descriptor, policy, shape, layout, residency, mutability, alignment, overflow,
and alias validation before entering the reference loop.

The first runtime integration should split that implementation internally into:

```text
validate descriptors
  -> canonical CpuGemmProblem
  -> deterministic plan
  -> execute selected variant
```

The public symbol, generated backend, status ordering, error messages, and
reference loop remain unchanged initially.

## Architecture decisions for the first implementation

### Typed Matcore IR v1

Add `matcore::mdslc::ir::v1` as a documented semantic IR. Do not reinterpret
or mutate the v0 capture DTO.

The first typed model must make these properties first-class:

- typed operation kind;
- element and accumulation dtype;
- rank and structured static/dynamic dimension expressions;
- structured stride expressions, layout, memory space, and minimum alignment;
- buffer mutability plus operation read/write effects;
- explicit alias preconditions;
- synchronization semantics;
- typed target/fallback policy;
- semantic capability requirements;
- site ID, canonical callee, source location, and exact source/argument ranges;
- source bindings needed by the unchanged rewrite path.

The existing GEMM maps to symbolic dimensions:

```text
lhs: [m, k], strides [k, 1]
rhs: [k, n], strides [n, 1]
out: [m, n], strides [n, 1]
```

Detected CPU features and selected implementations are not part of the
target-independent IR. They belong to downstream capability and plan records.

### Version boundary

- JSON v0 remains byte-for-byte stable and retains its exact-member parser.
- The v0 golden remains immutable.
- v0-to-v1 conversion starts only from verified v0.
- v1-to-v0 projection rejects every property that v0/codegen cannot represent.
- JSON v1 receives an independent deterministic parser, serializer, verifier,
  golden, and explicit schema/version dispatch.
- Unknown versions fail; they are never retried as another version.
- Early live integration always verifies v1 but generates through the checked
  v0 projection, preserving generated bytes.
- `mdslc++` later requests v1 explicitly; an extractor default is not changed
  implicitly.

The stable site-ID domain and generated `_v0` suffix remain unchanged while
the output is provably the same runtime ABI v0 lowering. If later typed-v1
codegen emits non-equivalent private wrappers/backends, that lowering must use
a distinct symbol/ABI suffix to prevent weak-symbol collisions with v0 objects.

### CPU capability record

Add a standalone, versioned record with only facts used by implemented CPU
variants:

```text
CpuCapabilitiesV1
  version
  architecture
  detection_complete
  fixed feature bitmask
  usable_vector_bits
```

Initial feature bits need portable scalar f32, AVX2, and FMA. AVX-512 is added
only when an implemented candidate has an exact requirement for it. Discovery
must avoid the legacy LLVM/MLIR runtime, GPU probes, subprocesses, unordered
sets, or speculative cache/topology values. Tests inject synthetic records.
Incomplete discovery is conservative: feature-specific variants become
illegal, while the portable reference remains legal.

### Variant registry and deterministic planner

Use a fixed-order registry, not dynamic static registration. Each entry has:

- a stable variant ID;
- an exact capability bit requirement;
- a pure legality function;
- an optional deterministic estimate;
- an execution function pointer.

Planning consumes typed operation semantics, a concrete validated
`CpuGemmProblem`, an injected capability record, and an explicit request mode.
It records every candidate's legality/reason and chooses using a documented
stable tuple, never link or registration order.

The first production registry contains only `cpu.reference.f32.v0`. Tiled and
compiler-vectorized candidates may enter forced/test mode after independent
correctness coverage. They become eligible for automatic selection only after
bounded performance evidence supports an explicit deterministic rule. A forced
illegal variant returns an error and never falls back.

### Diagnostics

Planning returns a structured deterministic report rather than printing to
ambient stdout. It contains planner version, concrete M/N/K, capability names
in canonical order, request mode, candidate decisions, selected stable ID, and
selection reason.

The existing one-shot C ABI remains intact. An additive versioned C plan/report
API may be introduced after the internal planner is stable; no C++ type crosses
the ABI.

## Legacy reuse boundary

Legacy `runtime_capabilities.cpp` and `target_registry.cpp` provide useful
ideas: requested-target/runtime-capability separation, fail-closed legality,
and CPU feature discovery. They are not direct dependencies because they also
bring LLVM containers, global/lazy GPU ownership, dynamic runtime probing,
subprocesses, and legacy target types.

Legacy `cpu_lowering.cpp` is MLIR/JIT substrate. Its tiling is prior art, not a
runtime planner implementation. `executor.cpp` and MLIR memref/JIT ABIs remain
excluded.

## Test contract

### IR and conversion

- v0 golden parse/re-serialize remains byte-identical;
- v0 -> v1 -> checked v0 projection reproduces JSON and generated artifacts;
- v1 parse/serialize is byte-identical;
- native/bootstrap converted-v1 semantics match except producer;
- shared m/k/n relationships and strides are verified;
- dtype/accumulation, layout, alignment, memory, mutability, effects, aliases,
  synchronization, policy, source order, and unique site IDs are verified;
- malformed, unknown, spoofed, and lossy projections fail actionably.

### Capability and planner

- synthetic feature matrices and incomplete detection;
- stable formatting and fixed feature order;
- unique registry IDs and deterministic repeated selection;
- reference selected for every currently supported shape/capability record;
- forced unavailable and no-candidate cases fail without fallback;
- deterministic candidate rejection reasons and tie-breaking.

### Runtime and performance

- retain all existing status-code, validation-order, and output-unchanged tests;
- add seeded rectangular/tail shapes and independent double-precision oracles;
- independently force every implemented candidate;
- rerun Release, Debug, ASan/UBSan, package, consumer, and artifact gates;
- add an opt-in benchmark target with warmup, median/p95, checksum, declared
  capability/variant/compiler metadata, and no global speed claim;
- keep performance benchmarks out of default CTest until a stable regression
  policy exists.

## Rollback-safe implementation sequence

1. Add ADR 0003 and direct C++ tests freezing JSON v0 compatibility.
2. Add the typed v1 model and verifier with no production integration.
3. Add verified v0-to-v1 conversion and loss-checked v1-to-v0 projection.
4. Add deterministic JSON v1 and explicit schema/version dispatch.
5. Exercise v1 in the extractor while generating through the checked v0
   projection; prove all generated files remain byte-identical.
6. Add standalone CPU capability discovery with injected unit-test records.
7. Add a pure fixed registry/planner with reference-only production selection.
8. Route the existing runtime v0 implementation through validate/plan/execute
   without changing generated code or public ABI.
9. Add structured plan diagnostics and an additive C ABI only if required.
10. Add a tiled forced candidate, correctness tests, and opt-in performance
    evidence; only then consider automatic ranking, vectorized code, or BLAS.

The next exact engineering checkpoint is step 1: freeze the v0 compatibility
contract and record ADR 0003 before adding any v1 production code.
